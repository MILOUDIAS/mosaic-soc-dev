# Architecture

MOSAIC-SoC is a generator. It reads one YAML file and writes a multi-core
RISC-V system on chip (SoC): the register-transfer-level (RTL) description, the
linker scripts and boot images for its software, a testbench, and the inputs of
a physical-design flow. It is a fork of [X-HEEP](https://github.com/x-heep/x-heep),
a single-core microcontroller platform, and it keeps X-HEEP's build system. The
SoC module `mosaic_soc` and its pad-ring wrapper `mosaic_system` are X-HEEP's
`core_v_mini_mcu` and `x_heep_system` under this project's names.

This page describes the generated SoC, then the generator that produces it, then
where each part lives in the repository.

## The generated SoC

```
            +---------------------- cpu_subsystem ----------------------+
            |  hart 0        hart 1            ...          hart N-1    |
            |  core          core + SCI wrapper             core + SCI  |
            +----|--|----------|--|---------------------------|--|------+
                 instr/data OBI master ports, two per hart
                              |
        +---------------------v----------------------+   debug master
        |   bus fabric: obi | log | floonoc          |<-- DMA masters
        +--|--------|-----------|----------|------|--+
           |        |           |          |      |
         RAM     debug     always-on    user    flash
         banks   module    peripherals  periph. window (XIP)
                           (soc_ctrl, boot ROM, SPI, DMA,
                            TDU, CLINT, power manager)
```

### Cores and roles

A *hart* is one hardware thread; in this project every core has exactly one. The
configuration lists core groups, and each group has an IP name, an instruction
set, a count and a *role*:

| Role | Meaning |
|---|---|
| `titan` | The orchestrator. It leaves reset running and boots from the boot ROM. |
| `atlas` | A worker. It leaves reset dormant and runs only after it is woken. |
| `nano` | A worker of the smallest class, with the same dormant behaviour. |

A design with workers has exactly one `titan`, placed first. A design made only
of `titan` harts is a symmetric multiprocessor and is also legal. Fourteen cores
are registered; [cores.md](cores.md) lists them.

### The Standard Core Interface

X-HEEP speaks OBI (Open Bus Interface), a simple request/grant bus with a
separate response-valid signal. Most of the supported cores do not. Each such
core has a wrapper in `hw/sci/<core>_sci.sv` that converts the core's native bus
to OBI and gives every core the same outer contract, called the Standard Core
Interface (SCI):

- OBI master ports for instruction fetch and data access (one merged port for
  cores with a single memory interface);
- a `fetch_enable_i` input that keeps a worker dormant, and a `core_sleep_o`
  output that reports it;
- interrupt inputs on the standard RISC-V positions (bit 3 software, bit 7
  timer, bit 11 external);
- a boot address parameter.

Cores without a native fetch-enable are held in reset, with their bus requests
masked, until they are woken. The four OpenHW cores (cv32e20, cv32e40p,
cv32e40px, cv32e40x) already speak OBI and are instantiated directly.

### Bus fabric

`soc.bus` selects one of three interconnects. All three present the same master
and slave ports to the rest of the design.

| Value | Implementation |
|---|---|
| `obi` | X-HEEP's N-to-M OBI crossbar (`system_xbar.sv.tpl`). The default. |
| `log` | A logarithmic interconnect (`tcdm_interconnect`) over word-interleaved RAM banks for memory traffic, and the OBI crossbar for everything else. |
| `floonoc` | A FlooNoC AXI network on chip with one router, generated by `floogen` from the topology that `util/mosaic_gen/floonoc_gen.py` emits, with OBI-to-AXI and AXI-to-OBI bridges at the endpoints. |

The number of bus masters is two per hart, one for the debug module, and the DMA
ports.

### Memory

| Region | Address | Notes |
|---|---|---|
| RAM banks | `0x0000_0000` | `memory.sram_kb`, or absent when it is 0 |
| Debug module | `0x1000_0000` | optional (`soc.debug`) |
| Always-on peripherals | `0x2000_0000` | includes the TDU at `0x200A_0000` and the CLINT at `0x200B_0000` |
| User peripherals | `0x3000_0000` | |
| Flash window | `0x4000_0000`, 16 MB | memory-mapped SPI flash, used for execute in place (XIP) |
| External slaves | `0xF000_0000`, 16 MB | off-chip RAM for `memory.external` |

Three memory profiles exist:

- **On-chip SRAM pool.** `memory.sram_kb` from 8 to 512. The TITAN boots from
  the boot ROM; worker images are placed in RAM at their `boot_addr`.
- **No on-chip SRAM, execute in place.** `memory.sram_kb: 0`. Every hart
  fetches its code directly from the flash window. An optional
  `memory.scratchpad_bytes` adds a small writable memory of 64 to 512 bytes,
  which is what gives the C runtime a stack.
- **No on-chip SRAM, external RAM.** As above, with `memory.external` declaring
  an off-chip writable region in the external-slave window.

The reasoning behind the last two is in
[design-notes/external_memory_boot_design.md](design-notes/external_memory_boot_design.md)
and [design-notes/area_study_gf180_min_soc.md](design-notes/area_study_gf180_min_soc.md).

### Peripherals

The always-on domain carries the SoC controller, the boot ROM, the SPI flash
subsystem, the DMA, the power manager and, optionally, a timer, a GPIO block and
a fast interrupt controller. The user domain carries what `soc.peripherals`
lists: `uart`, `gpio`, `timer`, `spi`, `i2c` and `serial_link`. These blocks come
from X-HEEP and OpenTitan.

`soc.spi_mode: xip_only` keeps only the read-only flash reader (`obi_spimemio`)
and removes the general SPI host.

### Task Dispatch Unit

The Task Dispatch Unit (TDU, `hw/tdu/rtl/tdu.sv`) is a memory-mapped block that
the TITAN uses to start work on the other harts. It is enabled by
`scheduler.tdu: true` and is required whenever the design has workers.

| Offset | Register | Purpose |
|---|---|---|
| `0x00` | `CORE_STATUS` | which harts are asleep (read only) |
| `0x04` | `SCHED_MODE` | `static`, `dynamic` or `power-aware` |
| `0x08` | `WAKE_MASK` | which harts may be woken |
| `0x0C` | `WAKE_REQ` | write a one to pulse the wake line of a hart |
| `0x10` | `TASK_PUSH` | enqueue a task descriptor |
| `0x14` | `TASK_POP` | dequeue a task descriptor |
| `0x18` | `TASK_STATUS` | queue occupancy |
| `0x1C` | `ACTIVE_HART_CYCLES` | cycle count with any hart active |
| `0x20` | `CPI_EST[n]` | per-hart cycles-per-instruction estimate, one word per hart |
| `0x60` | `PARK_REQ` | written by a worker when it finishes a task; the hart is parked again and its next wake restarts it from its boot address |

The task queue holds eight descriptors. A descriptor carries a task identifier,
a priority and a `core_hint` naming the hart that should run it. Software on the
TITAN chooses the target; the hardware preserves the choice.

### Interrupt controllers

- `mosaic_clint` (`hw/tdu/rtl/mosaic_clint.sv`) gives each hart one software
  interrupt and one 64-bit timer comparator, at the conventional RISC-V CLINT
  register offsets.
- The platform-level interrupt controller (PLIC) is OpenTitan's `rv_plic`. Its
  checked-in form has one interrupt target, so `util/mosaic_gen/plic_gen.py`
  regenerates it for the number of harts in the configuration. `soc.plic: false`
  removes it, which leaves peripheral interrupts with no route to a hart.

The platform services (PLIC, debug, TDU) support at most 16 harts.

### DMA

`soc.dma` selects the direct memory access engine:

| Value | Meaning |
|---|---|
| `idma` | pulp-platform iDMA with its register frontend, N-dimensional midend and OBI backend, wrapped by `idma_mosaic_wrapper`. Two streams, each with one read and one write OBI master. The default. |
| `none` | No DMA and no DMA bus masters. For area-critical designs that never copy bulk data. |
| `xheep` | X-HEEP's simple DMA. Accepted only for single-core configurations, because it has a different number of master ports. |

## The generator pipeline

```
mosaic.yaml
    |  1. validation        util/mosaic_gen/core_registry.py
    v
resolved configuration      util/mosaic_gen/mosaic_config.py, xheep.py
    |  2. template rendering  util/mosaic_gen/mcu_gen.py  (Mako, *.sv.tpl)
    |  3. software layout     util/mosaic_gen/software_gen.py
    v
build/mosaic/<name>-<hash>/   generated RTL, linker scripts, boot manifest
    |  4. FuseSoC             scripts/fusesoc-setup.sh
    v
resolved file list
    |-- 5a. Verilator         tb/mosaic_soc/run*.sh
    `-- 5b. LibreLane         flow/librelane/experimental/run_signoff.sh
```

1. **Validation.** `validate_soc_config` in `core_registry.py` checks every key,
   every value and the cross-field rules (for example, that a worker's reset
   address lies in a region that exists). The generator and the harness call the
   same function. Nothing is generated from a configuration that fails.
   [configuration.md](configuration.md) is the reference.
2. **Template rendering.** The RTL that depends on the configuration is written
   as Mako templates with the suffix `.sv.tpl`. `mcu_gen.py` renders them from
   one configuration object.
3. **Software layout.** `software_gen.py` writes linker scripts, a memory-map
   header, start-up code and `boot_images.json`, which lists the boot image each
   group of harts runs and where it is loaded.
4. **The bundle.** Everything generated goes into
   `build/mosaic/<soc-name>-<hash>/`. The hash covers the configuration and the
   contents of `hw/`, `tb/`, `util/`, `configs/`, `sw/`, `flow/` and `scripts/`,
   so the directory name identifies its inputs. `manifest.json` in the bundle
   records them. Two configurations never overwrite each other, and a physical
   run records which bundle it consumed.
5. **FuseSoC.** FuseSoC is the build system that resolves the dependency graph
   of `.core` files into an ordered file list. `scripts/fusesoc-setup.sh` runs
   it against a staging tree in which the bundle's generated files overlay the
   repository sources.
6. **Consumers.** The Verilator runners build a simulation model from that file
   list ([verification.md](verification.md)). The LibreLane runner hardens it
   into a layout ([physical-flow.md](physical-flow.md)).

The command for steps 1 to 5 is:

```bash
make mosaic-gen MOSAIC_CFG=configs/mosaic_wake_demo.yaml
```

`make mcu-gen` is the single-core X-HEEP generation path, kept for the upstream
configurations in `configs/*.hjson`. It renders the templates in place.

## Repository layout

| Path | Contents |
|---|---|
| `mosaic.yaml` | the default configuration |
| `configs/` | shipped configurations ([configuration.md](configuration.md)) and X-HEEP's base files |
| `util/mosaic_gen/` | the generator; `core_registry.py` is the single source of supported cores, buses, PDKs and configuration rules |
| `hw/mosaic_soc/` | the SoC templates: top level, CPU subsystem, bus, memory, peripherals |
| `hw/sci/` | the SCI wrappers |
| `hw/tdu/` | the TDU and the CLINT |
| `hw/vendor/mosaic/` | vendored cores, iDMA, FlooNoC and the bus bridges |
| `hw/vendor/` (other) | upstream X-HEEP, OpenHW, pulp-platform and OpenTitan IP |
| `hw/asic/` | technology-specific cells (clock gate, pads, SRAM wrapper) |
| `sw/` | device libraries, firmware and linker scripts |
| `tb/` | testbenches ([verification.md](verification.md)) |
| `flow/librelane/` | the physical flow ([physical-flow.md](physical-flow.md)) |
| `harness/` | the `mosaic` command-line tool ([agent-harness.md](agent-harness.md)) |
| `.claude/skills/`, `plugins/mosaic/`, `.omp/` | agent skill cards and host integration |
| `test/test_mosaic_gen/` | the Python test suite |
| `scripts/` | `fusesoc-setup.sh` and the regression sweep |
| `tools/` | the container launcher described in [reproducing.md](reproducing.md) |
| `build/` | all generated output; not version controlled |
